# Live plugin presentation (v1)

An installed Rust plugin can publish one semantic view for both minimal default adapters through `CallContext::present(View)`. The host receives serialized data at `eden.presentation.host.v1`; it derives the owner from the calling package, assigns a revision, and stores the view in the live Session. `CallContext::remove_view(id)` removes only that owner's view. The exact native host/SDK handshake for this release is `eden-native-0.6.0`; the C ABI remains version 1. Use the matching SDK source and [native installation rules](native-plugins.md).

`View::new(id, slot, title).node(...)` is the small typed builder. Nodes are text, code, Diff, table, group, attachment reference, status, form and button. Every node has a stable ID within its view; replace the view with the same owner and view ID to stream a new revision while frontends retain their local field drafts and scroll state. A view carries a plain fallback. `platforms` empty means the same standard content is offered to TUI and Web; a named platform contribution must declare `tui` or `web` and the other adapter shows its fallback. Standard task information and required actions must remain portable.

Panel and tool-result slots append in deterministic slot/owner/view order. Header, footer, overlay and composer are exclusive while a view is active; another owner or view receives `SlotConflict`. A run's views become inactive when the run settles, and shutdown closes publication. Native editor replacement remains a separate platform API; presentation does not carry terminal buffers, React elements, CSS, ANSI text or callbacks across the ABI.

## Forms and actions

Register `eden.presentation.action.v1` on the package and handle a typed `ActionRequest`; it is addressed by package owner, even when several installed packages provide that contract. Host admission checks Session ID, owner, live run, view ID, revision, action name and form values before dispatch. Text, fixed choice, multiple fixed choices and boolean fields exclude password and authentication data. Form IDs, field IDs and action names must be unique within a view. A form's first valid submission is claimed; other attachments see `handled_actions` in the next snapshot and receive `AlreadyHandled` if they submit independently. A handler failure releases the claim so the form can be retried.

Give every action attempt a stable `request_id` of at most 256 bytes. Reusing it with the identical request returns the same result, including after the calling HTTP connection disappears; reusing it with different input returns `DuplicateId`. The Web adapter retains uncertain attempts in tab session storage and offers **Retry last request** after refresh; the terminal adapter keeps the attempt ID while its process lives and uses Ctrl+r to retry an uncertain response. A browser or terminal keeps its draft locally until acceptance. Ordinary `prompt` while a run is busy returns the existing Session's `Unavailable` result and does not queue. Explicit `/enqueue` uses the existing `steering` or `follow_up` queue and also accepts a stable request ID for retry; there is no cross-type global FIFO. Cancellation is signalled with `/cancel`, and the run's settled state is the completion barrier.

Existing `eden.interaction.v1` select, confirm, input and editor requests map to owner `eden-host-interaction` form views when a live frontend is available. A dismiss button replies with null. The original `interaction_requested` and `interaction_finished` events and `respond_interaction` embedding API still work. An ordinary headless Session returns `Unsupported` for an interactive presentation; an explicitly started shared host retains a pending request after all frontends disconnect, subject to the author's existing timeout. Authentication stays on its private channel and never enters presentation or input activity.

## Shared local host

Build the Web adapter with `pnpm install --frozen-lockfile && pnpm js:check`, then start a new local task with an explicit endpoint file:

```sh
eden --composition /path/to/composition.json live --endpoint /path/to/live-endpoint.json --web-root /path/to/eden-agent/web/presentation/dist
eden live-tui --endpoint /path/to/live-endpoint.json
```

The first command owns one Session in a separate process and binds only `127.0.0.1`. It prints its address and writes the address, exact Session ID and a random local token to the endpoint file (mode `0600` on Unix). Open `http://ADDRESS/?token=TOKEN` from that file for the React/Spectrum adapter. An unspecific new client does not choose a Session from cwd or recency; each terminal client receives the endpoint path, and each browser receives the explicit URL. Starting another host creates another task. `eden live` rejects an existing history path rather than treating historical recovery as live attachment. `eden --history PATH` remains the separate read-only path; restoring stopped history remains explicit through the existing session commands.

The host HTTP API accepts `POST /attach`, `/detach`, `/activity`, `/prompt`, `/enqueue`, `/action`, `/cancel`, `/interaction` and `/shutdown`, plus `GET /snapshot?after=SEQUENCE&attachment=ID`. Every API request carries `X-Eden-Token` from the endpoint file. The snapshot is atomic for semantic views, pending mapped dialogs and input activity, with a monotonically increasing sequence; a late or lagged adapter reads another snapshot. Session IDs serialize as decimal strings in presentation JSON because JavaScript numbers cannot preserve every 64-bit ID. An attachment heartbeat accompanies snapshots; an abnormal disconnect clears its activity after four seconds and expires its attachment after ten seconds. A normal detach clears immediately. Disconnecting all adapters never cancels the run; only explicit cancellation or host shutdown does. Existing CLI print, in-process embedding and stdio RPC keep their own lifetimes.

Both adapters hold drafts, focus and scroll locally. They publish only composer or shared form activity targets, never draft text. Activity starts on edits, not focus, and clears on submit, edit pause, detach or lease expiry. Platform-specific editors can report the same public activity target; authentication and password fields cannot. The minimal adapters demonstrate the contract; complete terminal and browser product shells are separate work.

## Source and static projection handoff

`View.source` binds a live view to an optional originating record sequence and one `ContentClass`: `message`, `tool`, `thinking`, `full_output`, `attachment` or `extension`. These map one-to-one to the existing JSONL export selection flags `messages`, `tools`, `thinking`, `full_outputs`, `attachments` and `extensions`. The host already assigns `LiveView.run_id`; a view with no resolved `source.record_sequence` stays live-only until SP-B can associate it with a committed record in that run. An attachment node separately names its source record sequence. The title, fallback, nodes and their local reading operations inherit the view's source class: a static projector must drop the entire derived view when that class or record is excluded, then remove individual attachment references when attachments are excluded. It must not preserve an excluded text fragment in a title, fallback or link target. History copy/fork must remap both view source and attachment record references. A view without an explicit `Source` is also live-only because its filtering provenance is unknown. Static reading must keep the portable structure and remove business actions; a missing plugin must not be loaded for reading. SP-B implements record association, persistence, copy/remapping, export filtering and cross-version read fallback using these fields. This live API does not write static presentation records.

The independent native author at `tests/contract-authors/presentation-live` publishes a table, Diff, attachment reference, validated form, status update and terminal-only fallback. `python3 scripts/verify-presentation.py` checks its installed library through an independent host process, two attachments, streaming, retry, cancellation and a question created after the final detach. The Web adapter builds in the JavaScript check; the same author is usable for real Ratatui PTY and browser checks.
